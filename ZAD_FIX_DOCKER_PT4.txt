### **PART 1: THE PRODUCTION-FIRST MANDATE (THE BLUEPRINT)**

This is the strategic plan that must be followed to get the "all-purpose" factory live.

#### **Step 1: Containerize the FINAL, REAL System**

Before any deployment, you will assemble the final, production-ready version of the entire application into a single, cohesive Docker Compose configuration.

* **Requirement**: Create a new `docker-compose.prod.yml` file. This file must:
    1.  Formalize the RAG-enhanced factory core (currently in `step2-factory-test.ts`) into the official `factory-core` service.
    2.  Include the container for the **REAL**, UEP-enabled `backend-agent` that was refactored and tested in Phase 3.
    3.  Integrate the containers for all other **REAL** meta-agents (e.g., `frontend-agent`, `devops-agent`, etc.).
    4.  Include all necessary production infrastructure: NATS, Redis, and a persistent database like PostgreSQL.
* **NO FAKE SHIT**: There will be **ZERO** placeholder containers or simplified "test" agents. Every service in this file must be the final, production-ready version from the repository. If any agent is not complete or has bugs, **YOU ARE TO GO FIX THE AGENT IMMEDIATELY.** Do not proceed with a partial or broken swarm.

**DO NOT PROCEED TO STEP 2 UNTIL `docker-compose -f docker-compose.prod.yml up` RUNS SUCCESSFULLY ON A LOCAL MACHINE.**

#### **Step 2: Achieve a Stable Staging Deployment**

Once the production configuration runs locally, you will deploy the exact same configuration to a cloud-based, production-like staging environment.

* **Requirement**:
    * Provision a clean staging environment (e.g., a new cloud server or Kubernetes cluster).
    * Deploy the entire application using the `docker-compose.prod.yml` from Step 1.
    * The goal is a "green" deployment: all containers must be running, passing their health checks, and able to communicate with each other over the cloud network.
* **NO FAKE SHIT**: This cannot be a "localhost" deployment. It must be on a remote server with real networking, firewalls, and environment variables. If you encounter permissions errors, networking issues, or environment-specific bugs, **YOU ARE TO DEBUG AND FIX THE DEPLOYMENT SCRIPTS AND CONFIGURATIONS IMMEDIATELY.** Do not manually SSH into containers to fix things; the deployment must be repeatable and automated.

**DO NOT PROCEED TO STEP 3 UNTIL THE ENTIRE SWARM IS STABLE AND HEALTHY IN THE STAGING ENVIRONMENT.**

#### **Step 3: Conduct Full-Scale User Acceptance Testing (UAT)**

With the system running in a real environment, you will validate the quality and correctness of its output using a complex, real-world PRD.

* **Requirement**:
    1.  Using the Web UI on the **staging URL**, submit a large, complex, and realistic PRD (e.g., for a "Social Media Analytics Dashboard").
    2.  Monitor the project's entire lifecycle from the UI, from task generation to completion.
    3.  Once the project is complete, you must manually review all generated artifacts (code, documentation, deployment scripts) to ensure they are high-quality, correct, and align with the PRD.
* **NO FAKE SHIT**: This is not a "hello world" test. The PRD must be complex enough to require coordination between at least 3-4 different agents. The goal is not just to see if the system *runs*, but to prove that the final output is **actually useful and correct**. If the generated code is buggy or the output is nonsensical, **YOU ARE TO DEBUG THE AGENT'S CORE LOGIC, THE RAG'S CONTEXT, OR THE FACTORY'S PLANNING IMMEDIATELY.**

**DO NOT PROCEED TO STEP 4 UNTIL A COMPLEX PROJECT HAS BEEN SUCCESSFULLY COMPLETED AND THE OUTPUT IS VERIFIED TO BE OF HIGH QUALITY.**

#### **Step 4: Implement and Validate Production Monitoring**

Once the system's output is proven to be correct, the final step is to establish full visibility into the deployed system's operational health.

* **Requirement**:
    * Integrate the Prometheus and Grafana monitoring stack with the live, deployed services in the staging environment.
    * Create a new Grafana dashboard named "Agent Swarm Operations".
    * This dashboard must provide real-time visibility into:
        * The health and status of each individual agent.
        * The volume of UEP messages on the NATS bus.
        * The number of active, pending, and completed tasks.
        * Resource usage (CPU, memory) for the factory and key agents.
* **NO FAKE SHIT**: This cannot be a demo dashboard with static data. It must be connected to the **REAL**, live data from the staging environment. The metrics must be meaningful and actionable. If you cannot get a metric to appear, **YOU ARE TO FIX THE AGENT'S METRICS EXPORTATION OR THE PROMETHEUS CONFIGURATION IMMEDIATELY.**

**THE MANDATE IS COMPLETE ONLY WHEN YOU HAVE A STABLE, DEPLOYED SYSTEM PRODUCING HIGH-QUALITY OUTPUT, WITH A FULLY FUNCTIONAL OPERATIONS DASHBOARD.**
